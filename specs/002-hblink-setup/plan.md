# Implementation Plan: HBLink + HBMonv2 Setup and Analysis (P0)

**Branch**: `002-hblink-setup` | **Date**: 2026-05-25 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification at `specs/002-hblink-setup/spec.md`

## Summary

Install HBLink3 and HBMonv2 on the dev server using the ShaYmez Docker installer, resolve Apache virtual host coexistence with the existing CFLAG DMR application, and produce a complete written analysis of HBLink's internal structure. This analysis is the prerequisite input for every CFLAG DMR management feature (F2–F8). No CFLAG DMR application code is written in this phase.

## Technical Context

**Language/Version**: Bash (installer), Docker Compose v2 (HBLink container), Python 3.x with venv (HBMonv2), PHP 8.x (existing CFLAG DMR — unchanged), Apache2 (shared web server)

**Primary Dependencies**: [ShaYmez/hblink3-docker-install](https://github.com/ShaYmez/hblink3-docker-install) — one-shot Bash installer. Docker and Docker Compose v2 installed by the script.

**Storage**: HBLink config files at `/etc/hblink3/` (INI + Python). HBMonv2 lastheard database at `/opt/HBMonv2/` (format: TBD during analysis — likely SQLite). HBLink log at `/var/log/hblink/hblink.log`.

**Testing**: Manual verification (service status checks, browser load tests, reboot test). No automated test framework.

**Target Platform**: Linux dev server (Debian 11/12/13 or Ubuntu 22.04/24.04 LTS). Apache2. HTTP only (dev).

**Project Type**: Infrastructure setup + analysis/documentation phase. Not a user-facing feature.

**Performance Goals**: N/A — this is a one-time setup and analysis operation.

**Constraints**:
- The HBLink installer is destructive — pre-install backup is mandatory.
- The installer installs its own Apache2 configuration that will conflict with the existing CFLAG DMR vhost. This must be resolved manually post-install.
- No CFLAG DMR application code is written in this phase.
- The analysis document must reflect observed facts from the live server, not documentation paraphrases.

**Scale/Scope**: Single dev server, single HBLink instance, one-time operation.

## Responsibility Breakdown by User Story

### US1: HBLink and HBMonv2 installed and verified

**Actions**:
1. Run pre-install backup (Apache config, CFLAG DMR project).
2. Record current Apache virtual host state (`apache2ctl -S`).
3. Clone and run the installer from `/opt/hblink3-docker-install`.
4. Verify HBLink container is running: `docker compose ps` in `/etc/hblink3/`.
5. Verify HBLink log is clean: `docker container logs hblink | tail -50`.
6. Verify HBMonv2 service is active: `systemctl status hbmon`.
7. Verify config files present: `ls /etc/hblink3/hblink.cfg /etc/hblink3/rules.py`.

**Done when**: All 7 checks pass with no errors.

---

### US2: Apache coexistence resolved

**Actions**:
1. Diff Apache config before and after install: `diff -r /root/apache2-backup-YYYYMMDD /etc/apache2/`.
2. Identify the HBMonv2 Apache vhost config created by the installer.
3. Reconfigure HBMonv2 vhost to port 8080:
   - Add `Listen 8080` to `/etc/apache2/ports.conf`.
   - Change `<VirtualHost *:80>` to `<VirtualHost *:8080>` in the HBMonv2 vhost file.
4. Restore CFLAG DMR vhost if overwritten (from backup); re-enable with `a2ensite`.
5. Run `apache2ctl configtest` — must report `Syntax OK`.
6. Run `systemctl reload apache2`.
7. Verify CFLAG DMR loads at `http://<server-ip>/`.
8. Verify HBMonv2 loads at `http://<server-ip>:8080/`.
9. Run `apache2ctl -S` to confirm document roots are fully separated.

**Done when**: Both apps load without errors. Apache config test passes. Document roots confirmed separate.

---

### US3: Full written analysis committed

**Methodology**: Read each file directly from the server. Write findings into `specs/002-hblink-setup/analysis.md`. Commit when all required sections are complete.

**Required sections** (see `data-model.md` for full schema):

1. **`hblink.cfg` structure** — All section types (`[MASTER_*]`, `[PEER_*]`, `[OBP_*]`, `[Parrot]`, etc.); key fields per section; example values; what each section controls. Inspection: `cat /etc/hblink3/hblink.cfg`.

2. **`rules.py` structure** — Python data structure layout; how a talkgroup-to-system routing rule is defined; field names; annotated example. Inspection: `cat /etc/hblink3/rules.py`.

3. **Log format** — Startup sequence (first clean startup output); transmission event entry (if available from live traffic or test transmission); fields per log line. Inspection: `cat /var/log/hblink/hblink.log`, `docker container logs hblink`.

4. **Last-heard data store** — File path (found by: `find /opt/HBMonv2 -name "*.db" -o -name "*.sqlite"`); format (SQLite, flat file, MySQL, other); schema if structured (`.schema` in sqlite3); fields and their meaning; update frequency. If empty, document structure from schema only.

5. **Reload and restart behaviour** — Whether HBLink supports config reload without full restart (check `docker-compose.yml` and HBLink source for SIGHUP handling); what happens to active calls during restart; exact commands for reload vs. restart vs. full down/up.

6. **Annotated directory listing** — `find /etc/hblink3 /opt/HBMonv2 -not -path '*/venv/*' -not -path '*/__pycache__/*' | sort`; each file/directory described in one line.

7. **Integration points** — Every mechanism CFLAG DMR can use: config files (read/write), log file (tail), HBMonv2 DB (read), report socket port 4321 (protocol TBD), WebSocket port 9000 (for future use); access requirements per integration point; recommended approach for each CFLAG DMR feature.

**Done when**: All 7 sections complete with no "TBD" entries. Document committed to repo.

## Rollback Plan

1. **If installer breaks CFLAG DMR**:
   ```bash
   # Restore Apache config from backup
   cp -r /root/apache2-backup-YYYYMMDD/. /etc/apache2/
   systemctl reload apache2
   # Verify CFLAG DMR loads
   curl http://localhost/
   ```

2. **If HBLink install needs to be removed**:
   ```bash
   hblink-uninstall
   # or: cd /etc/hblink3 && docker compose down
   ```
   Note: `hblink-uninstall` backs up configs to `/root/hblink3-backup-[timestamp]` before removing.

3. **Full server rollback** (if VM snapshot was taken before install):
   Restore the VM snapshot from the hosting provider console. This is the cleanest option if the install leaves the server in an unrecoverable state.
