# Implementation Plan: F2 — Role & Permission System

**Branch**: `003-role-permissions` | **Date**: 2026-05-25 | **Spec**: [spec.md](spec.md)

---

## Summary

Replace the flat `admin_users` authentication model with an extensible role-based permission system. Introduce a `users` table as the canonical identity store, a `roles`/`user_roles` join-table design for multi-role assignment, and a `moderation_state` field that independently controls website access and DMR network whitelist inclusion. Migrate existing admin records transparently. Provide a `require_role()` guard function that all subsequent features use for access control.

---

## Technical Context

**Language/Version**: PHP 8.x — `declare(strict_types=1)` on all files

**Primary Dependencies**: None. Plain PHP, PDO, MariaDB. No Composer.

**Storage**: MariaDB — `cflag_dmr_dev` database. 6 tables created/modified (see data-model.md).

**Testing**: Manual verification via browser + direct DB inspection. Test scenarios in quickstart.md.

**Target Platform**: Linux server (Debian/Ubuntu), Apache 2.4, PHP 8.x

**Project Type**: Web application (server-side rendered, admin panel + future public pages)

**Performance Goals**: Standard page response. Role check = one JOIN query per request; acceptable at this scale.

**Constraints**: No Composer, no framework, no JavaScript build tools. Session-based auth.

**Scale/Scope**: Tens of admin/moderator users initially. Schema designed to grow to thousands without redesign.

## Implementation Sequence

Tasks are ordered to minimise risk. The schema and data layer ship first; the UI comes last. At each step, the site remains functional.

### Step 1 — Database migrations (no app changes yet)

Apply in order:
1. `002_create_users_roles_tables.sql` — creates all new tables
2. `003_seed_system_roles.sql` — seeds the four system roles
3. `004_migrate_admin_users.sql` — migrates existing admins to `users` table

After this step: both `admin_users` and `users` tables exist. The site still works because `login.php` still queries `admin_users`.

### Step 2 — `app/auth/roles.php` (new file)

Provides the permission layer. No side effects — just function definitions.

Key functions and their contracts:

```php
// Role hierarchy constant
const ROLE_HIERARCHY = ['user' => 1, 'moderator' => 2, 'admin' => 3, 'system_admin' => 4];

// Returns the logged-in user's row from `users`, or null.
// Reads from session (user_id) + one DB query for moderation_state.
function current_user(): ?array

// Returns true if the user holds any role with level >= the given role.
// Fetches roles fresh from DB on each call (no session caching).
function user_has_role(int $user_id, string $min_role): bool

// Returns array of role name strings the user holds.
function get_user_roles(int $user_id): array

// Calls require_login(), then user_has_role(). On fail: redirect to /admin/ with 403 header.
function require_role(string $min_role): void

// Assign a role to a user. Enforces: actor cannot assign roles above their own level.
// Enforces: at least one system_admin must always exist.
// Writes to user_roles + audit_log. Throws on violation.
function assign_role(int $actor_id, int $target_id, string $role_name): void

// Revoke a role from a user. Same enforcement as assign_role.
// Writes to user_roles (DELETE) + audit_log.
function revoke_role(int $actor_id, int $target_id, string $role_name): void

// Insert a row into mod_log.
function log_mod_action(int $actor_id, int $target_id, string $action,
                        string $reason, ?int $duration_hours = null,
                        ?string $expires_at = null): void

// Insert a row into audit_log.
function log_audit_action(int $actor_id, string $action_type,
                          string $target_type, ?int $target_id,
                          array $detail = []): void

// Insert a pending row into config_change_queue.
function queue_network_regen(int $actor_id, string $change_type, array $details = []): void
```

### Step 3 — Update `app/auth/session.php`

Changes:
- Replace `is_admin()` + `require_admin()` with `is_logged_in()` + `require_login()`
- `is_logged_in()`: `isset($_SESSION['user_id']) && is_int($_SESSION['user_id'])`
- `require_login()`: if not logged in, redirect to `/login.php`
- Keep `start_session()`, `csrf_token()`, `verify_csrf()`, `redirect()` unchanged

Remove: `is_admin()`, `require_admin()` (replaced by `require_role()` in roles.php)

### Step 4 — Update `app/auth/login.php`

Changes:
- Query `users` table instead of `admin_users`
- After `password_verify()`, check `moderation_state`: if `suspended` or `banned`, return false
- On success: set `$_SESSION['user_id']` (integer), `$_SESSION['username']`, `$_SESSION['display_name']`
- Remove `admin_id` and `admin_username` session keys
- Call `session_regenerate_id(true)` on success (already present)
- Update `last_login_at` in `users` table (not `admin_users`)

Error message for suspended/banned: the function returns false; the caller shows the same generic "Invalid username or password." message as a credential failure — no distinction is revealed (FR-011).

### Step 5 — Update `public/login.php` and `public/logout.php`

`login.php`: no functional change to the page itself — just benefits from the updated `app/auth/login.php`.

`logout.php`: clear `user_id` from session (was `admin_id`). No other changes.

### Step 6 — Update `public/admin/index.php`

Replace `require_admin()` call with `require_role('admin')`. No other changes.

### Step 7 — New pages: user list and user detail

`public/admin/users/index.php`:
- Calls `require_role('system_admin')`
- Paginated table: username, display_name, roles (comma-joined), moderation_state, last_login_at
- Each row links to `view.php?id={user_id}`
- Mobile-first layout (table scrolls horizontally on small viewports)

`public/admin/users/view.php`:
- Calls `require_role('admin')`
- Shows user detail: username, email, DMR ID, moderation_state, tier, created_at
- **Role management section** (system_admin only):
  - Current roles listed with "Revoke" button per role
  - Dropdown to add a new role (limited to roles ≤ actor's level)
  - CSRF-protected POST form
- **Moderation section** (admin+ for suspend/ban; moderator+ for network mute):
  - Current moderation_state with label
  - For `active` users: "Mute on network" (duration selector + reason), "Suspend" (reason), "Ban" (reason)
  - For `suspended` users: "Lift suspension" button (admin+)
  - For `banned` users: "Reverse ban" button (system_admin only)
  - For `muted_on_network` users: "Lift mute" button (moderator+)
  - All actions are CSRF-protected POST forms

### Step 8 — `scripts/expire-mutes.php`

PHP CLI script. Designed to be run as: `php /opt/cflag-dmr/scripts/expire-mutes.php`

Logic:
1. Require `app/config/env.php` and `app/database/connection.php`
2. SELECT all users WHERE `moderation_state = 'muted_on_network' AND mute_expires_at IS NOT NULL AND mute_expires_at <= NOW()`
3. For each: UPDATE users SET moderation_state='active', mute_expires_at=NULL
4. `log_mod_action(system_admin_id, user_id, 'auto_expired', 'Timed mute expired automatically')`
5. `queue_network_regen(system_admin_id, 'moderation_state_change', [...])`
6. Output: one line per expired mute (for cron logging)

Cron entry (add to server crontab):
```
* * * * * php /opt/cflag-dmr/scripts/expire-mutes.php >> /var/log/cflag-dmr-cron.log 2>&1
```

## Security Checklist

- [ ] All DB queries use PDO prepared statements (no string interpolation)
- [ ] All HTML output is escaped with `htmlspecialchars($val, ENT_QUOTES, 'UTF-8')`
- [ ] All POST forms include CSRF token validation via `verify_csrf()`
- [ ] `require_role()` is called at the top of every protected page before any output
- [ ] Login denial for suspended/banned accounts uses the same generic message as credential failure
- [ ] Role assignment enforces actor-level ceiling (no privilege escalation)
- [ ] Last-system-admin guard prevents locking out all admins
- [ ] `mute_expires_at` is only set when `moderation_state = 'muted_on_network'`; cleared on any state change away from that state
- [ ] `config_change_queue` rows are only inserted when `dmr_id IS NOT NULL` on the target user (no regen needed for users without a DMR ID)
